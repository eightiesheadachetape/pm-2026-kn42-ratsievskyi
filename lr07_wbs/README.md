Спосіб перевірки: Перевірку виконано арифметичним підсумовуванням трудомісткості всіх дочірніх пакетів 3-го рівня, сума яких строго відповідає батьківським пакетам 2-го рівня та кореню проекту (1820 годин). Також залучено валідатор курсу.

Робота, яку ледь не забули: Налаштування CI/CD конвеєра в Docker та первинну міграцію довідників системних баз практик.

Що свідомо поза обсягом:
- Мобільний застосунок для студентів (працюємо виключно через адаптивний браузерний веб-інтерфейс).
- Пряма автоматична інтеграція з ЄДЕБО у першому релізі.

## 4. Критичний шлях

Дата старту робіт: 2026-07-06. Тиждень це п'ять робочих днів, свята не рахуємо.

| Що | Значення |
| --- | --- |
| Критичний шлях, робочих днів | 100 |
| Ланцюг критичних робіт | T-01 → T-02 → T-03 → T-05 → T-06 → T-07 → T-10 → T-12 → T-13 → T-14 |
| Дата завершення за планом | 2026-11-20 |
| Строк мого варіанта, робочих днів | 100 |
| Різниця | 0 |

Чи вкладаємось: Так, календарний план чітко відповідає 100 робочим дням (20 тижнів) варіанта V12.

Що з цим робимо: Оскільки тривалість критичного шляху строго дорівнює дедлайну, будь-яке відхилення на критичному шляху призведе до зсуву дати релізу. Для мінімізації ризиків розробку допоміжних модулів (T-08, T-09, T-04) винесено на паралельні гілки з достатнім резервом часу (float_days).

Робота з найбільшим резервом: T-11 (Супровід ризиків та комунікації) має резерв 55 днів, оскільки виконується паралельно та не блокує подальші етапи кодування та тестування.
