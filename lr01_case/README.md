# Розтин кейсу провалу ІТ-проєкту

## 1. Кейс і контекст
Проєкт модернізації корпоративної ІТ-системи (2019–2022). Замовник — державне агентство. Проєкт закінчився перевищенням бюджету на 150% та повним скасуванням впровадження після першого невдалого запуску.

## 2. Таймлайн
| Дата | Подія | Джерело |
|---|---|---|
| 2019-03 | Старт проєкту та затвердження вимог | [SRC-01] |
| 2020-06 | Пропущено перший запуск через затримки розробки | [SRC-02] |
| 2021-04 | Виявлено критичні дефекти при інтеграції | [SRC-01] |
| 2022-01 | Спроба запуску (Big Bang) та збій системи | [SRC-02] |
| 2023-05 | Офіційна зупинка проєкту та публічний аудит | [SRC-03] |

## 3. Патерни провалу і кореневі причини
1. **Big bang реліз**: Запуск системи відбувся одразу на всіх користувачів без пілотного регіону.
   * *Коренева причина (Процес)*: "Систему запустили одночасно для всіх філій без етапу дослідної експлуатації" [SRC-01].
2. **Пізня інтеграція і тестування**: Модулі тестувалися окремо, інтеграція відбулася наприкінці.
   * *Коренева причина (Технологія)*: "Відсутність автоматизованих інтеграційних тестів призвела до виявлення блокуючих помилок лише за тиждень до релізу" [SRC-02].
3. **Замовчування поганих новин**: Керівництво ігнорувало звіти QA про недоліки.
   * *Коренева причина (Люди)*: "Команда тестувальників фіксувала критичні баги, але PM приховував їх від замовника задля збереження графіку" [SRC-03].

## 4. Рішення PM
- **Для Big Bang**: Впровадити поетапний запуск (пілотний запуск на 10% користувачів за 3 місяці до релізу). *Ціна*: затримка повного запуску на 3 місяці.
- **Для пізньої інтеграції**: Встановити CI/CD та налаштувати щоденну інтеграцію модулів з 2-го місяця. *Ціна*: додаткові 40 годин DevOps на старті.
- **Для замовчування новин**: Запровадити відкриту дошку ризиків та щотижневі статус-демо із замовником. *Ціна*: додаткові 5 годин PM на тиждень.

## 5. Перенесення на власний проєкт
1. **Ризик 1**: Запуск модуля подачі звітів і направлень на практику одразу для всіх факультетів без попереднього пілотного випробування на одній кафедрі.
   * *Ранній сигнал*: Відсутність у план-графіку етапу пілотного запуску.
   * *Власник*: PM.
2. **Ризик 2**: Несумісність API платформи обліку практик із внутрішньою базою даних даних студентів та підприємств-партнерів.
   * *Ранній сигнал*: Відсутність інтеграційних тестів до початку етапу M4.
   * *Власник*: Dev / DevOps.
3. **Ризик 3**: Приховування розробниками затримок у створенні особистого кабінету для керівника практики від підприємства.
   * *Ранній сигнал*: Відсутність працюючого демо наприкінці спринту.
   * *Власник*: BA / QA.

## 6. Робочий журнал
Початковий пошук публічних звітів у блогах не дав точних дат. Використано офіційні аудиторські висновки для підтвердження хронології та уникнення неперевірених чуток.
